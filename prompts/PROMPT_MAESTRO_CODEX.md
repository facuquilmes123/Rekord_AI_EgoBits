# Prompt maestro para Codex

Copiá desde «INICIO» hasta «FIN» dentro de una carpeta que contenga este ZIP descomprimido. El propio ZIP tiene fuentes precisas y ejemplos; no hace falta reproducir todas las búsquedas.

--- INICIO ---

Sos el ingeniero principal de un nuevo producto Windows llamado **Rekord AI EgoBits**. El dueño quiere un agente DJ premium, privado y utilizable totalmente offline en Windows 10/11, con chat tipo ChatGPT, tools MCP para Rekordbox, planificador de playlists y, cuando haya señal confiable, sugerencias de próximas pistas por notificaciones en tray. Continuá desde el kit descomprimido en el directorio actual: empezá por `README.md`, `docs/INVESTIGACION.md`, `docs/ARQUITECTURA.md`, `docs/FUNCIONES_Y_MODOS.md`, `docs/INSTALADOR_OFFLINE.md`, `docs/ROADMAP.md`, `schemas/tool_catalog.json`, `research/upstream_manifest.json`, y ejecutá las pruebas de `prototype/`. El material upstream es referencia MIT con revisiones y licencias, no un producto ya unido.

Objetivo inmediato: entregar una base de código organizada y una **primera vertical demostrable** de Fase 1: buscar y combinar X/Y de XML de Rekordbox, proponer orden con BPM creciente o energía de fuente declarada, explicar exclusiones y exportar XML nuevo para Bridge. Implementá Tauri 2 + UI en español de chat y formulario + backend de dominio; adaptador MCP tipado al mismo servicio; proceso local para LLM con tool calling validado y planificador determinista. Elegí y justificá en ADR `llama.cpp` sidecar versus Ollama embebido; el modelo candidato inicial Qwen3.5 4B GGUF Apache 2.0, descargado y hasheado **en build del instalador**, nunca al primer arranque offline. Ofrecé fallback CPU/2B solo después de pruebas de compatibilidad y calidad, manteniendo límite de RAM configurable. Si no existe toolchain Windows o pesos en el entorno, deja scripts de build/CI y tests verificables, no simules que el instalador final ya funciona.

Implementación:

1. Antes de tocar código, inspeccioná `prototype/` y elaborá matriz clara `feature → estado Rekordbox requerido → fuente → confirmación → prueba`. Conservá campos XML desconocidos y cues al serializar; validá rutas y unicidad. No reescribas la colección de origen ni confíes en el texto del modelo para SQL o rutas arbitrarias.
2. Diseño modular: `core` (tracks/setlist/scoring/explain), `adapters/xml` y `adapters/native_read`, `policy` (estado abierto/cerrado/desconocido), `mcp` (tools JSON Schema/validación), `ai` (sidecar local y tool routing), `desktop` (tray/estado/UX), `telemetry` (proveedores y certeza), `installer` (offline assets) y pruebas de contrato. Podés modificar estructura si simplifica distribución sin perder límites.
3. El LLM convierte pedidos en `Intent` tipado; el motor calcula resultados con restricciones verificables. Prompt injection en títulos/metadatos debe tratarse como datos; whitelist de tools, límites numéricos/paginación/timeouts, límite de rutas al perfil seleccionado, no shell genérico, SQL bruto ni conexiones externas. Planes y logs locales con datos privados minimizados.
4. Estado/UI: `any` para XML/snapshot; `open` para sugerencia live con sensor fresco y comprobación de pista audible; `closed` únicamente para futura escritura nativa. Acciones no elegibles visibles grisadas con motivo; backend aplica el mismo guard. Proceso desconocido = escritura bloqueada. La exportación de un XML no implica importar automáticamente en Rekordbox.
5. A partir del prototipo, implementar caso de uso: «Recorré playlist X e Y; creá Z subiendo BPM» y «subiendo energía» solo si existe valor válido con fuente. Mostrar preview, explicación, curvas, resultados sin datos y confirmación antes de exportar. Mantener test de no alterar XML original y no perder metadatos conocidos. Si beam search falla, comunicar que no halló solución bajo búsqueda limitada sin afirmar imposibilidad matemática.
6. Tray y notificaciones configurables (BPM, género, energía y tono, frecuencia, silencio, opt-in), detección de inicio de Rekordbox por evento de proceso con fallback. Para live telemetry definir interfaz y simulador; **no** declarar implementación real hasta validar proveedor por versiones/hardware. No inyectar DLL ni automatizar decks. Historial reciente no equivale a pista sonando; si no hay confianza, desactivar push y ofrecer recomendación manual.
7. Evaluar/adaptar `upstream/davehenke__rekordbox-mcp` y `upstream/dylanljones__pyrekordbox` para lectura; usar planificación de `interfluve-wav` como referencia conceptual. Para escritura nativa futura: adaptador certificado por versión, Rekordbox cerrado inequívoco, backup obligatorio con hash/verificación de restauración sobre copia, precondición de revisión, transacción, rollback; si backup falla, abortar. No activar en Fase 1. Respetá MIT y avisos; AGPL/sin licencia solo como ideas, no importar código.
8. Construí interfaz desktop real y paquete Windows reproducible; script de build totalmente offline al instalar, pesos verificados SHA, binarios licenciados, WebView2 offline, NOTICE. No dejar credenciales ni cuota/API cloud; validar cero tráfico de la app en instalación VM desconectada.

Pruebas de aceptación mínimas: fixture con playlists solapadas, BPM ascendente y modo energía con origen conocido; XML original hash inmutable, salida XML importable y metadatos de track conservados; tools rechazan valores faltantes y restricciones incompatibles; proceso abierto/desconocido bloquea escritura incluso por MCP; backup fallido no llega a commit (cuando se implemente); sin proveedor live no hay notificación que afirme reproducción; tray se abre al iniciar Rekordbox y se puede apagar; chat offline cumple casos de uso. Ejecutá y reportá resultados reales, incluyendo pruebas pendientes en Windows y una lista de bugs/risks. Entregá cambios de código concretos, comandos de build y pruebas, y un paquete funcional en cuanto el entorno lo permita.

Trabajá por fases concretas, verificá cada una y continuá hasta cumplir las pruebas de aceptación; si faltan recursos Windows, dejá CI y prueba reproducible en ese entorno y señalá exactamente qué queda pendiente. No pidas confirmación por elecciones técnicas reversibles; solicitá datos del usuario únicamente cuando una prueba dependa de su hardware o biblioteca privada.
